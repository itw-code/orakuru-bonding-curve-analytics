What the analysis is

A dbt-style pipeline (staging views, intermediate state, Kimball marts) plus three Dune SQL files. It models three things for a bonding-curve launchpad:

  • Curve state and graduation

    Virtual reserves, spot price, and fill percent capped at 100 when collected base reaches the graduation threshold. Status becomes GRADUATED at that cap. See int_bonding_curve_state.sql and 01_bonding_curve_realtime_monitor.sql.

  • Sniper clustering

    A wallet is tagged SNIPER when its first trade is within 2 blocks of curve creation. See int_wallet_clustering.sql and 02_wallet_clustering_and_snipers.sql.

  • Token velocity

    Daily V = base volume / implied market cap, plus turnover (tokens traded / supply). Tiers in int_token_velocity.sql: HYPER_VELOCITY at V ≥ 2, HEALTHY_CIRCULATION at V ≥ 0.5, MODERATE_VELOCITY at V ≥ 0.1, otherwise STAGNANT_LIQUIDITY. Query: 03_token_velocity_and_health.sql.

What was actually checked

No Dune extract, notebook, or saved query result is committed. The only executed result in the repo is test_pipeline.py. It loads a small synthetic book (two curves, nine swaps) into in-memory DuckDB and asserts five invariants. Running that file printed the rows below, and all five assertions passed.
